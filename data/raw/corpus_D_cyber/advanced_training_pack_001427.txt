STEP 1: INITIAL TRIAGE (5 minutes)
Tools and commands:

    print(pe.OPTIONAL_HEADER.AddressOfEntryPoint)
    for section in pe.sections:
        print(section.Name, section.VirtualAddress, section.SizeOfRawData)

Key indicators in strings output:
  - URLs/IPs: C2 infrastructure
  - Registry paths: Persistence mechanisms
  - File paths: Dropped payloads, config files
  - API names: Capability fingerprinting
  - Error messages: Often left in by developers
  - Mutex names: Identify malware family, prevent re-infection

STEP 2: IMPORT TABLE ANALYSIS
Suspicious DLL imports:
  WS2_32.dll  → Network communication
  WININET.dll → HTTP/FTP client
  ADVAPI32.dll → Registry, cryptography, services
  CRYPT32.dll → Certificate/crypto operations
  NTDLL.dll   → Direct Windows internals (syscalls)

High-risk API combinations:

  CreateFile + ReadFile + CryptEncrypt = Ransomware
  RegSetValueEx + Run key strings = Registry persistence
  WSAStartup + socket + connect = Network communication
  LoadLibrary + GetProcAddress = Dynamic API resolution (evasion)

STEP 3: ENTROPY ANALYSIS
  import scipy.stats
  import math
  def calculate_entropy(data):
      if not data:
          return 0
      counter = Counter(data)
      length = len(data)
      probs = [count / length for count in counter.values()]
      return -sum(p * math.log2(p) for p in probs if p > 0)

Entropy interpretation:
  < 5.0: Normal code or data
  5.0-7.0: Compressed or partially encrypted
  7.0-7.5: Compressed (UPX, zlib)
  > 7.5: Encrypted or high-entropy packed section
  = 8.0 (maximum): Perfect encryption (AES-encrypted payload)

If entire file is high entropy:
  → Packed (try UPX: upx -d malware.exe)
  → Custom packer: Requires dynamic unpacking

--- CODE ANALYSIS: COMMON MALWARE PATTERNS ---

PATTERN 1: API HASHING (Evasion of import detection)
Instead of: LoadLibrary("kernel32.dll") + GetProcAddress("VirtualAlloc")
Malware does:
  uint32_t hash_api(const char* api_name) {
      uint32_t hash = 0;
      while (*api_name) {
          hash = (hash >> 13) | (hash << 19);  // ROR 13
          hash += *api_name++;
      }
      return hash;
  }
  // Walk PEB.Ldr.InMemoryOrderModuleList
  // For each export, hash name, compare to target hash
  // Hash of "VirtualAlloc" = 0x97BC257U (varies by algorithm)

Deobfuscation approach:
  1. Run sample in debugger, break on dynamic API resolution
  2. Log all resolved functions
  3. For static analysis: Implement hash function, create lookup table

PATTERN 2: STRING ENCRYPTION (XOR)
Common implementation:
  char encrypted[] = { 0x7C, 0x53, 0x45, 0x42, ... };  // "http://" XOR'd
  char key = 0x15;
  for (int i = 0; i < sizeof(encrypted); i++) {
      encrypted[i] ^= key;  // Decrypt in place
  }

Python decryptor script:
  encrypted = bytes([0x7C, 0x53, 0x45, 0x42])
  key = 0x15
  plaintext = bytes([b ^ key for b in encrypted])
  print(plaintext.decode('utf-8', errors='replace'))

For multi-byte XOR key:
  from itertools import cycle
  key = b"\xDE\xAD\xBE\xEF"
  plaintext = bytes([b ^ k for b, k in zip(encrypted, cycle(key))])

PATTERN 3: PROCESS HOLLOWING (with assembly walkthrough)
High-level:
  1. CreateProcess(..., CREATE_SUSPENDED, ...)   // Create suspended target
  2. GetThreadContext(hThread, &ctx)             // Get thread context
  3. ReadProcessMemory(...)                      // Read current base address from PEB
  4. NtUnmapViewOfSection(...)                   // Hollow out target PE
  5. VirtualAllocEx(hProcess, imageBase, ...)    // Allocate space for payload
  6. WriteProcessMemory(hProcess, imageBase, ...) // Write payload
  7. SetThreadContext(hThread, &ctx)             // Set EIP to payload OEP
  8. ResumeThread(hThread)                       // Execute payload in target process

x64 specifics: EAX (x86) → RAX (x64) for entry point in context
PEB offset: ctx.Rdx+16 = pointer to ImageBase in PEB

Detection: Sysmon Event ID 8 (CreateRemoteThread),
           Event ID 10 with CallTrace containing RWX memory regions

PATTERN 4: SLEEP OBFUSCATION (Avoiding memory scanning)
Modern technique: Encrypt beacon in memory while sleeping
  1. Register timer/APC callback
  2. When sleeping: Encrypt beacon payload in-memory (Ekko, Foliage techniques)
  3. Re-register callback for wakeup
  4. On wakeup: Decrypt beacon, execute C2 communication
  5. Re-encrypt before next sleep

Detection: Look for RWX memory regions that change entropy while process sleeps
           Use PE-sieve periodic scanning to detect anomalies

RECOGNIZING COMPILER CONSTRUCTS:
Virtual function call (C++):
  mov rax, [rcx]           ; Load vtable pointer from 'this'
  call [rax + 0x18]        ; Call virtual function at vtable offset 24

Stack canary check (gcc -fstack-protector):
  mov rax, [rbp-0x8]       ; Load stored canary
  xor rax, fs:0x28         ; Compare with TLS stored canary
  jne error_handler        ; Jump if mismatch (stack smashed)

Optimized loop (unrolled by compiler):
  xmm0 = load 16 bytes at once
  pcmpeqb xmm0, xmm1       ; Compare 16 bytes in parallel
  pmovmskb eax, xmm0        ; Create bitmask from comparison
  test eax, eax

--- MEMORY CORRUPTION FUNDAMENTALS ---

STACK BUFFER OVERFLOW (Classic):
Vulnerable C code:
  void vulnerable(char *input) {
      char buffer[64];
      strcpy(buffer, input);  // No bounds check
  }

Stack layout (x86):
  [buffer (64 bytes)][saved EBP (4 bytes)][saved EIP (4 bytes)][args...]
  Overflow: Fill buffer + 4 bytes (overwrite EBP) + 4 bytes (overwrite EIP)

Finding offset with pattern:
  python3 -c "import sys; sys.stdout.buffer.write(b'Aa0Aa1Aa2Aa3Aa4Aa5...')" > input
  gdb -q ./vuln
  run < input
  # EIP value = offset in De Bruijn pattern
  python3 -c "from pwn import *; print(cyclic_find(0x61413361))"

x64 differences:
  - RIP control requires overwriting return address at rbp+8
  - Calling convention: rdi, rsi, rdx, rcx, r8, r9 for first 6 args
  - Stack must be 16-byte aligned before CALL
  - ASLR + PIE: Must leak address before ROP
  - NX/DEP: Can't execute shellcode on stack; use ROP chains

RETURN-ORIENTED PROGRAMMING (ROP):
Goal: Chain existing code snippets ("gadgets") ending in RET
Finding gadgets:
  ROPgadget --binary vuln --rop --badbytes "00"
  ropper -f vuln --search "pop rdi; ret"
  pwndbg: rop --binary vuln

Building ROP chain (Linux x64 execve /bin/sh):
  # Goal: execve("/bin/sh", NULL, NULL)
  # syscall number 59 = execve
  # Arguments: rdi=/bin/sh pointer, rsi=0, rdx=0, rax=59

  from pwn import *
  elf = ELF('./vuln')
  rop = ROP(elf)

  # Step 1: Write "/bin/sh" to writable memory
  rop.raw(pop_rdi)           # pop rdi; ret
  rop.raw(writable_addr)     # address to write "/bin/sh"
  rop.raw(pop_rax_rdi_rsi)   # gadget to set up write syscall

  # Step 2: Set up execve arguments
  rop.raw(pop_rdi)
  rop.raw(binsh_addr)        # pointer to "/bin/sh"
  rop.raw(pop_rsi)
  rop.raw(0)                 # NULL (argv)
  rop.raw(pop_rdx)
  rop.raw(0)                 # NULL (envp)

  # Step 3: Set rax = 59 and syscall
  rop.raw(pop_rax)
  rop.raw(59)
  rop.raw(syscall_ret)       # syscall; ret

HEAP EXPLOITATION:
Common vulnerability classes:
  Use-After-Free: Access freed memory after realloc → type confusion
  Double-Free: Free same chunk twice → heap metadata corruption
  Heap Overflow: Write past allocated chunk boundary
  Uninitialized Heap: Read sensitive data from previously freed memory

ptmalloc internals (glibc malloc):
  Chunk layout:
    [prev_size (8 bytes if prev free)][size (8 bytes)][data...][fwd][bk (if free)]
  Size field flags: PREV_INUSE (0x1), IS_MMAPPED (0x2), NON_MAIN_ARENA (0x4)
  Bins:
    Fast bins: 0x20-0xb0, singly linked, no consolidation
    Unsorted bin: All freed chunks first go here
    Small bins: 0x20-0x3f0, doubly linked
    Large bins: > 0x3f0, doubly linked with skip pointers

Tcache exploitation (glibc 2.26+):
  Per-thread cache, 7 entries per size class
  Single-linked, no integrity check in early versions
  tcache poisoning: Overwrite next ptr in freed chunk
  → next allocation returns fake chunk at attacker-controlled address

Example:
  # After freeing chunk at 0x555555559260 twice (double-free):
  # tcache: 0x559260 -> 0x559260 (loop)
  # Allocate to reach second entry, overwrite next with target (e.g., __free_hook)
  # Allocate again → returns __free_hook
  # Write system() to __free_hook
  # free("/bin/sh") → system("/bin/sh")

--- EXPLOIT MITIGATIONS AND BYPASSES ---

1. STACK CANARIES:
  Bypass methods:
    a. Information leak: Read canary via format string, off-by-one
    b. Brute force (forking servers): Try values, detect crash vs no-crash
    c. Overwrite with correct value: If we know canary value
  Format string canary leak:
    printf("%23$p")  # Print 23rd argument (often canary on stack)

2. ASLR:
  Bypass methods:
    a. Information leak: Leak pointer from stack/heap/binary
    b. Partial overwrite: Only overwrite lower bytes (12 bits not randomized)
    c. Spray: Fill large memory areas with shellcode (old technique)
    d. ret2plt: Use PLT entries (fixed offsets from binary base)
  With PIE disabled: Binary at fixed address; only libraries randomized

3. NX/DEP:
  Bypass: ROP chains (no code execution on stack needed)
  ret2libc: Classic technique
    pop_rdi; ret
    ["/bin/sh" address in libc]
    ret (for stack alignment)
    system() address in libc

4. RELRO (Relocation Read-Only):
  Partial RELRO: PLT entries still writable (GOT overwrite possible)
  Full RELRO: GOT entirely read-only at startup
  Bypass Full RELRO: Target other writable locations (__malloc_hook, __free_hook)
  In glibc 2.34+: __malloc_hook removed; use tcache/fastbin attacks instead

5. CFI (Control Flow Integrity):
  Restricts indirect branches to valid targets
  Coarse-grained CFI: All function pointers must point to function starts
  Fine-grained: Must match function signature
  Shadow stack: Hardware-enforced return address protection (Intel CET)
  Bypass: Find type confusion, use "valid" function with exploitable behavior

--- AWS SECURITY: ATTACK AND DEFENSE ---

AWS ATTACK SURFACE:
Common misconfiguration patterns:
  1. Public S3 buckets: s3://company-backup accessible without auth
  2. Overpermissive IAM roles: EC2 instance with AdministratorAccess
  3. Exposed metadata service: IMDSv1 accessible from web app (SSRF)
  4. Public RDS snapshots: Database backup downloadable by anyone
  5. Lambda environment variables: Secrets stored in plaintext env vars
  6. Exposed management ports: 22/SSH, 3389/RDP open to 0.0.0.0/0
  7. CloudTrail disabled: No audit trail of API calls

METADATA SERVICE EXPLOITATION (IMDSv1 vs IMDSv2):
IMDSv1 (vulnerable):
  curl http://169.254.169.254/latest/meta-data/iam/security-credentials/
  # Returns: role-name
  curl http://169.254.169.254/latest/meta-data/iam/security-credentials/MyRole
  # Returns: AccessKeyId, SecretAccessKey, Token, Expiration

SSRF exploit path:
  1. Find SSRF vulnerability in web app (e.g., image fetch by URL)
  2. Supply URL: http://169.254.169.254/latest/meta-data/iam/security-credentials/
  3. Receive EC2 instance credentials
  4. Use credentials with AWS CLI from attacker machine
  5. Escalate via instance role permissions

IMDSv2 (protected):
  # Requires PUT request first to get token
  TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
  # SSRF via GET cannot add PUT method → IMDSv2 blocks SSRF
  # Mitigation: Enforce IMDSv2 via instance metadata options

AWS PRIVILEGE ESCALATION PATHS:

--- TLS/SSL DEEP TECHNICAL ANALYSIS ---

TLS 1.3 HANDSHAKE (simplified):
Client                                          Server
  ClientHello (supported cipher suites,    →
    key_share: ECDH public key)
                                            ←  ServerHello (chosen cipher,
                                                key_share: server ECDH public key)
                                               {EncryptedExtensions}
                                               {Certificate}
                                               {CertificateVerify}
                                               {Finished}
  {Certificate} (optional mutual auth)     →
  {CertificateVerify} (optional)           →
  {Finished}                               →
  [Application Data]                       →←  [Application Data]

Key improvements over TLS 1.2:
  - Removed RSA key exchange (no forward secrecy)
  - Removed static DH key exchange
  - Removed CBC cipher suites (BEAST, POODLE, Lucky13 vulnerabilities)
  - Removed RC4 (biased keystream)
  - Removed export-grade ciphers (FREAK, Logjam)
  - 0-RTT resumption: First message encrypted (replay risk)
  - Encrypted handshake after ServerHello (SNI still visible)

  -T fields -e ip.src -e dns.qry.name -e frame.len | \

# Extract TLS certificates

# Find potential C2 beaconing

  -T fields -e frame.time_epoch -e ip.src -e ip.dst -e http.host | \
  python3 -c "
import sys, statistics
from collections import defaultdict
intervals = defaultdict(list)
prev = defaultdict(float)
for line in sys.stdin:
    t, src, dst, host = line.strip().split('\t')
    key = (src, dst, host)
    if prev[key]:
        intervals[key].append(float(t) - prev[key])
    prev[key] = float(t)
for k, v in intervals.items():
    if len(v) > 5:
        cv = statistics.stdev(v) / statistics.mean(v) if statistics.mean(v) > 0 else 999
        if cv < 0.15:
            print(f'Beacon: {k}, avg={statistics.mean(v):.1f}s, cv={cv:.3f}')
"

ZEEK (BRO) FOR NETWORK MONITORING:
Custom Zeek script for DGA detection:
  # detect_dga.zeek
  event dns_request(c: connection, msg: dns_msg, qtype: count, qclass: count) {
      local query = msg$query;
      # Calculate entropy of domain label
      local consonants = 0;
      local vowels = 0;
      local label = split_string(query, /\./)[0];
      for (i in label) {
          if (label[i] == "a" || label[i] == "e" || label[i] == "i" ||
              label[i] == "o" || label[i] == "u") {
              vowels += 1;
          } else if (label[i] != "-") {
              consonants += 1;
          }
      }
      # High consonant-to-vowel ratio = DGA indicator
      local ratio = consonants + 0.0 / (vowels + 1.0);
      if (|label| > 10 && ratio > 4.0) {
          NOTICE([$note=DGA_Detection,
                  $conn=c,
                  $msg=fmt("Potential DGA: %s (C:V ratio %.1f)", query, ratio)]);
      }
  }

--- STRUCTURED ANALYTIC TECHNIQUES (SAT) FOR CYBER ---

1. KEY ASSUMPTIONS CHECK
Before major security decision, list and test assumptions:
  Scenario: "We believe attackers exfiltrated customer data"

  Assumption 1: "The attacker had access to the database"
  Test: Check database access logs for attacker IP/account
  Challenge: Could they have accessed data via application layer?

  Assumption 2: "The 50GB outbound transfer was data exfiltration"
  Test: What was in the transfer? Examine proxy logs
  Challenge: Could be legitimate backup, sync, or CDN traffic

  Assumption 3: "The breach started 3 weeks ago"
  Test: Look for earliest indicator of compromise
  Challenge: Attacker may have been dormant for months

  Result: Document which assumptions are supported vs unverified
  Action: Investigate unsupported assumptions before reaching conclusions

2. COMPETING HYPOTHESES ANALYSIS (ACH)
For incident with ambiguous cause:

  | Evidence                     | H1:APT | H2:Insider | H3:Ransomware | H4:Script Kiddie |
  |------------------------------|--------|------------|---------------|------------------|
  | Custom malware used          | +      | neutral    | -             | -                |
  | Targeted specific files      | +      | +          | -             | neutral          |
  | Slow, quiet exfiltration     | +      | +          | -             | -                |
  | Used known ransomware tool   | -      | -          | +             | +                |
  | No ransom note               | +      | +          | -             | neutral          |
  | Used valid credentials       | neutral| +          | neutral       | neutral          |
  | Exfil to cloud storage       | +      | +          | neutral       | -                |

  Scoring: Count + (consistent) vs - (inconsistent)
  H1 (APT): 5+ vs 1- → Most consistent
  H2 (Insider): 4+ vs 0- → Possible
  H3 (Ransomware): 1+ vs 4- → Unlikely
  H4 (Script Kiddie): 1+ vs 3- → Unlikely

3. TEAM A/TEAM B RED TEAMING
Scenario: Security architecture review for new payment system

Team A (Defenders):
  Design: WAF + API gateway + HSM for card data + PCI DSS compliance
  Argument: Layered controls, industry standard, certified environment

Team B (Attackers — internal red team):
  Attack vectors:
    - WAF bypass via chunked encoding
    - API logic flaws: Race condition on payment idempotency key
    - HSM: Key ceremony compromise via insider
    - PCI scope reduction via network segmentation bypass
  Findings: API race condition allows double-spending

  Outcome: Team B finds critical logic flaw Team A's controls missed
  Resolution: Fix race condition before launch; add idempotency enforcement

TECHNICAL FINDING FORMAT (CVSS + Business Impact):
  Finding: SQL Injection in /api/v1/search endpoint
  Severity: Critical (CVSS 9.8 — AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
  Affected component: Product search functionality
  Impact: Unauthenticated attacker can read, modify, or delete all database contents
  Business impact: Full customer PII exposure (GDPR breach notification required),
                   intellectual property theft, service disruption
  Evidence: INSERT INTO users... via UNION SELECT
  Proof of concept: GET /api/v1/search?q='; DROP TABLE users;--
  Remediation: Parameterized queries (prepared statements); immediate priority
  Verification: Retest after fix; automated DAST in CI/CD pipeline

RISK SCORING MATRIX:
  Likelihood × Impact = Risk Score
  Likelihood:
    1 — Very unlikely: No known exploit, requires physical access
    2 — Unlikely: Complex exploit, limited threat actors capable
    3 — Possible: PoC exists, motivated threat actors
    4 — Likely: Actively exploited, easy exploit
    5 — Near certain: Automated exploitation at scale

  Impact:
    1 — Negligible: No sensitive data, no service disruption
    2 — Minor: Non-PII data, brief disruption
    3 — Moderate: PII for some users, hours of downtime
    4 — Major: PII for all users, days of downtime, financial loss
    5 — Critical: Full system compromise, data destruction, regulatory action

  Risk:
    1-4: Low (review quarterly)
    5-9: Medium (fix within 90 days)
    10-16: High (fix within 30 days)
    17-25: Critical (fix immediately)
